# Android 标准发版

先判断这次交付的是一段文案、一个可安装的包，还是完整发布材料。用户说“写一下 Git”时，读差异后直接给可复制的文案；截图是 GitHub New release 时，给表单字段和面向下载者的正文。两种请求都不隐含创建标签、提交、推送、上传或公开发布的授权。

## 核对发布身份

- 从 Android 应用模块的实际发行变体读取产品名、applicationId、versionName、versionCode、minSdk、正式站点和签名配置来源。沿用工程的 Gradle Wrapper、JDK、变体和既有发行流程。已有正式用户时，先找上一份可信的发行包或证书记录。
- 从当前仓库的工作区、差异（含已暂存和未跟踪文件）、分支及历史定位本次变更。网站、Android 和部署脚本可能处于不同仓库，也可能是同一远端的不同分支。发布目标应包含实际生成附件的提交；若提交尚未出现在可选远端目标上，说明待同步的提交，勿改选默认分支。
- 综合用户说明和已有公开 Release 判断首发或更新；源码标签、测试版、versionCode、非零的小版本号均不能单独证明已有正式版。如果无法确定且会改变发布正文，问一个问题。新项目默认准备侧载 APK 与 GitHub Release。
- 只写文案且缺少产物时，可先用已知文件名交付草稿，在表单外列出待核项。最低系统只采用已核实的 minSdk；只知道 targetSdk 或未注明用途的 API 数字时，先省略最低系统声明。公开发布前再核对候选包。

## 按请求交付

| 请求 | 操作与交付 |
| --- | --- |
| “签名怎么填”“生成正式版”“不能覆盖安装” | 按[签名、构建与升级](references/signing-and-upgrades.md)操作；分别核对身份、构建产物、最终附件。交付 APK 的真实路径。 |
| “部署好了，测一下” | 先确认本次涉及哪些组件。用[验收记录](assets/acceptance.md)分别记录线上资源、本地回归、指定设备和厂商真机证据。只填写相关场景。 |
| “写 Git 文案” | 依据各仓库或分支的实际差异填写[提交模板](assets/git-message.md)。一段对应一个可提交的变更集，外部部署配置单列交付。 |
| “写 Release” | 按[首个正式版](assets/release-first.md)或[后续更新](assets/release-update.md)输出表单字段、独立正文和本地附件路径。正文中的操作路径、文件名和系统版本应与实物一致。 |
| “准备完整发版” | 汇总发布身份、已验证的正式包、验收记录、Git 文案、Release 字段及待上线事项。README 按现有风格修正过期内容，无需统一章节。 |

保留新项目固定命名 `<产品名>-v<versionName>-release.apk`；历史项目保留既有升级及分发约定。新项目默认用 GitHub Release 归档 APK，源码提交只记录构建所需文件，不将安装包、密钥或密码纳入 Git。已使用其他产物归档方式的项目依原约定处理。

## 验收与权限

通过 `adb devices -l` 识别用户开启或指定的设备，后续命令带明确的序列号。已有锁或“already running”提示时先查设备清单与进程；未经授权不启动、重启或停止 AVD，不用删锁或卸载解决冲突。没有可用设备时照常交付已完成的构建和检查，列出设备待测项。测试后恢复切换过的外观、免打扰等设置。

依据操作名称区分“已生成正式签名包”“测试签名包连接生产站验证通过”“正式包在指定设备覆盖升级通过”。公开发布前核对远端目标、附件与验过的 APK 一致。发生签名冲突、目标不明或远端结果不明确时，保留现场并查询实际状态，避免重复发布。

调用示例：`使用 $android-standard-package 为这个内部版本准备首次公开发布的 GitHub 字段、中文正文和附件清单。`
