# 从业务提醒到 Android 系统通知

## 选择投递机制

从需求问到可观察结果：用户只要站内消息、前台提示，还是要退到桌面、锁屏后也能收到？是否同一账号多设备同时接收？网络恢复后补收是否满足时效？只有答案影响选型且项目资料未说明时，才询问用户。

先盘点已有调度、原生或厂商推送、Web Push、目标机型以及服务端修改权限。普通 Android 应用能显示系统通知，仍需有机制把业务事件送到设备。iOS 主屏应用按其 Web Push 授权与订阅验收；国内 Android 范围较广时，要核实 Google 服务依赖、厂商通道覆盖与接入条件。对可改后端、自用侧载、接受可见后台服务的项目，可以考虑标准 HTTPS 的自建连接。它依赖联网和系统允许后台运行；用对应机型验证锁屏、进程回收、待机和用户强行停止后的行为。把取舍写给用户，勿承诺所有机型在任何状态下准点送达。

## 可复用的 WePass 案例

1. **业务只计算一次。** 后端沿用已有计划调度与同伴催办，创建持久通知时考虑接收人、账号推送偏好、站内开关、免打扰与例外。已完成或已取消计划按原业务规则停止后续提醒；免打扰可按约定延迟或合并。已有服务器调度时，Android 再排同一条本地闹钟会重复投递。
2. **为每台设备保留独立进度。** 第一次经 HTTPS 用当前会话取得已认证账号和初始水位，首次是否跳过历史按产品规则确定。后续携带账号和各自游标，有积压时按序分页，处理后再保存游标并按通知 ID 去重。账号归属以服务端认证为准，返回前复核会话，换号时重置进度。离线重连用旧游标补收；设备 A 收到一条通知不应消耗设备 B 的投递机会。
3. **提交后唤醒全部在线设备。** 旧实现用四个同步网页线程处理业务，只给两个请求等待；第三台无消息时收到带重试间隔的业务响应，页面却误称手机网络异常。扩大线程数仍会让空闲设备长期占用网页线程。这里由独立异步监听器等待，普通网页请求和独立计划任务在事务提交后按账号发本机唤醒提示。服务用持久记录读正文，处理“读空与登记之间提交”的竞态；断线释放等待者，超时再读防止漏唤醒。
4. **区分续接与高频轮询。** 实例里空闲请求等待约 25 秒，期间不按 3 秒查库；有新消息就立即唤醒。25 秒超时是复查和续接时机。对旧服务的“容量已满”尊重 Retry-After，并区分未登录、网络中断和服务器不可用。参数根据客户端读取超时、代理和部署容量调整。
5. **设备收到后再产生系统通知。** 依平台版本处理通知权限及后台服务要求；检查系统总开关、学习提醒渠道、本机暂停、账号偏好和连接状态。低打扰的后台连接提示与业务提醒分别建渠道，让用户能单独调节。把切换账号、服务重启、网络切换及用户关闭权限纳入回归。

## 诊断页面应该回答什么

| 用户看到的问题 | 先区分 | 证据与呈现 |
| --- | --- | --- |
| Android 壳显示“当前环境不支持推送” | 网页是否错误地只检测浏览器 PushManager | 识别壳后读原生能力和账号偏好，普通浏览器／iOS 主屏应用走各自路径。旧版只能识别壳、不能报告实时状态时，明确提示在本机查看。 |
| 能打开网页却显示“正在重连” | 后台服务、会话有效期、HTTPS 代理、等待容量、本机权限分别如何 | 仅在已知原因时指向具体处理入口。连接中断或上次请求失败时说明自动重试，不把所有错误归为手机网络故障。 |
| 测试按钮成功却没看到通知 | 后端接受、查询到事件、系统入栏和锁屏展示分别是否发生 | 提交后提示“已提交”；用通知 ID 和触发时间核对设备系统通知。浏览器订阅投递历史不能替代 Android 收件结果。 |
| 点通知跳错账号或旧页面 | 当前会话、圈子／对象权限和最新清单是否匹配 | 仅打开仍可访问的目标，其他情况回到合适的通知入口。 |

覆盖同账号多会话同时等待、另一账号不被串送、被撤销的会话无法收件、事务回滚无投递、离线补收、重放去重、后台任务跨进程唤醒和等待期间网页健康可用。测试多条同时挂起的连接并观察空闲读库次数；快速发送多个顺序请求无法检验真实并发。
