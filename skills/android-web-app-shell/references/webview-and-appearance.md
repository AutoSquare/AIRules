# WebView、品牌与系统外观

## 导航与登录

- 先确定生产入口的 scheme、host、port 和首屏路由。固定站点直接进入正式 HTTPS；绑定型应用先定义扫码内容校验、解绑与恢复流程。生产和本地调试入口用可识别的构建变体分开，明文回环例外和 WebView 调试只用于相应测试包。
- 让站内导航、Cookie 登录和网页历史继续工作；外部 HTTP(S) 用系统处理器。主文档失败时提供重试，避免子资源失败替换整个页面。验证冷启动、刷新、返回键、旋转或恢复 Activity 后的状态。
- 仅向受信主页面开放必要的原生能力。按解析后的来源、主框架、允许的动作校验，敏感跳转再检查用户手势。例如从诊断页打开原生应用设置，可由固定内部 URI 触发；页面标记或 User-Agent 仅用于展示和能力识别。离开本站时停止注入。不要将会话 Cookie、令牌写进 URL、日志或 JS 接口返回值。
- 如果网站支持从系统通知打开目标，点击后重新确认当前账号及目标权限。必要时先刷新一次清单，再打开对应项目；对象已取消或无权访问时退到通知中心。退出或切换账号后清理上个账号的系统通知、待处理点击和会话相关状态。

## 文件、相机与下载

从真实网页按钮开始验收。文件选择器遵循 accept、多选与取消语义；调用相机按需使用临时内容 URI 和授权，回到网页只完成当前一次回调。区分网页媒体权限、系统相机调用和用户选择文件，按功能申请权限。

普通 HTTPS 附件和页面通过 Blob 生成的导出文件需要分别测试。对受保护附件仅向其可信来源携带必要会话，重定向时重新判断来源。Blob 属于页面上下文，应在对象有效时取得内容，再交给原生保存；留意网页导出后立即释放对象的时序。使用系统支持的下载／媒体存储方式，处理文件名、MIME、重名、取消和写入失败。检查最终文件内容可打开，单看“下载完成”提示无法发现下载到登录页等错误。

## 图标选择与验收

向用户展示导航 Logo、favicon、Web App Manifest、apple-touch-icon 及已有设计稿中实际存在的候选项。确认图案、是否带底、底色、主体比例与留白。用户曾明确要白底，结果第一次装到桌面却透出了壁纸；第二次加了底色，主体大小仍与网站主屏图标不同。因此要把网页添加到桌面的实际效果和 Android launcher 截图并排核对。在截图中区分浏览器生成的快捷方式徽标与原稿本身。

根据选定稿检查普通、圆形和自适应图标的裁切，适用时检查系统快捷方式与启动画面。桌面图标、页面 Logo 和通知栏小图标用途不同；通知栏使用清晰的单色轮廓。以实际桌面的显示为验收依据，避免只比对仓库中的 PNG 尺寸。

## 外观与跨端入口

在“跟随系统”场景沿着整条链检查：**系统 uiMode → Activity 亮／暗主题 → WebView 的 prefers-color-scheme → 页面主题 → 设置选项的选中状态**。固定浅色的应用主题会让网页一直得到浅色偏好。为暗色提供对应的原生主题资源，并核对窗口背景、状态栏、原生弹窗和网页首帧。网页已有自定义暗色设计时沿用其配色逻辑。

页面可通过稳定的应用 UA 标记在首屏识别新版壳，用功能探测判断能否打开原生入口。自动模式在 Android 壳显示「跟随系统」，浏览器显示「跟随浏览器」；手动浅色／深色持久化，系统变化仅驱动自动模式。只改字符串会留下行为错误，只改原生主题会留下网页文案错误。给实际部署的主题脚本更新资源版本。

验收时依次观察自动浅色、系统切暗、暗系统下选浅色、亮系统下保留手动深色、重新选自动；检查普通浏览器、已保存偏好的刷新和旧壳。窄屏诊断页把主操作与辅助入口分开，核对「应用设置」「查看站内通知」的高度、对齐和触控区域，并逐个点开；旧壳只显示确实支持的入口。
