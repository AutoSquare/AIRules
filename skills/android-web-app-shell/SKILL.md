# Android 网站壳

从零封装时，先读项目，再给用户方案。已有壳只修当前问题，例如“为什么还显示跟随浏览器”只需走外观与对应验证。不要因为网站有站内消息就默认建设后台推送服务。

## 从现有网站确定需求

1. 查实际用户入口、登录／绑定方式、站内外跳转、所用上传和导出方式，以及 PWA 图标、Service Worker 和现有通知链路。查看实际提供给用户的页面及部署目录，有些项目的正式 UI 在静态原型目录，而非框架默认入口。
2. 确认用户要的是固定生产地址，还是需要扫码或手工绑定服务。列出目标设备、最低系统、国内手机的服务依赖、允许修改的前后端、需要保留的浏览器／iOS 主屏能力。只问资料无法回答且会改变方案的问题。
3. 根据业务记录触发者、接收者和送达场景。例如“计划开始前提醒”须查现有调度、时区、提前量、完成／取消及免打扰规则；“添加到 iPhone 桌面后会提醒吗”须查授权、订阅与实际投递。把“写过逻辑”和“已在目标设备验证”分别说明。
4. **每次新封装或更换图标，都先由用户选择原稿。** 若当次任务中用户已经明确指认某张原稿，记录该选择即可；否则展示实际候选图或预览，注明来源、底色和用途，选定后再生成桌面图标。只有一张候选稿也先展示确认。等待选稿时可继续查工程或设计其他部分。单修通知、外观等其他问题不触发选稿。
5. 输出方案，列清网站、原生壳、后端各自负责的功能、待确认权限、兼容旧版本的方式和验收场景。让用户确认方案后再从零实施。用户已授权的范围继续有效；技术上可改后端不等于本次已授权部署生产环境。

## 按任务读取

| 当前任务 | 读什么，交付什么 |
| --- | --- |
| 开发基本壳、修复下载／导航、对齐图标和深浅色 | 读[网页与原生边界](references/webview-and-appearance.md)，交付能力分工、适配和可在设备上重现的检查。 |
| 国内 Android 锁屏提醒、网页推送诊断不准、多台设备互相挤掉 | 读[通知投递与诊断](references/notifications.md)，沿实际链路定位故障，从一条已提交的消息验证到系统通知或锁屏。 |
| 检查部署脚本、Nginx 或数据库是否需要改；验证已部署的站点 | 读[部署与设备验收](references/rollout-and-devices.md)，交付受影响组件、上线顺序、回退点和分层证据。 |

只有用户已开启或指定的设备才用于实测；未经明确授权不启动或重启 AVD。设备不可用时完成可独立运行的构建与本地回归，并明确记录待测场景。使用测试签名构建、回环调试站点或本地并发会话时，写清它们实际验证了什么。

调用示例：`使用 $android-web-app-shell 为这个网站规划 Android 客户端。重点确认国内手机锁屏后怎样收到提醒，以及用什么设备验收。`
